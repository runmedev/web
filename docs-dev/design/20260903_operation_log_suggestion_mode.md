# Operation-log suggestion mode

## Status

Implemented as an initial vertical slice for `.runme` notebooks.

## Decision

Suggestion mode is a projection of the existing append-only operation log, not a
second notebook format or review database. Editor operations produced by one
debounced snapshot change share a stable `suggestion_id`. Review decisions,
comments, and replies are additional operations in the same `.runme` file.

This keeps authored changes and their review history available to every replica
through the existing OPFS and Drive merge path. Legacy logs remain reviewable:
an operation without `suggestion_id` or `transaction_id` becomes a one-operation
suggestion.

## Data model

`RunmeOperation.suggestion_id` groups authored operations. The ID generated by
the editor journal is `<actor>:suggestion:<first actor sequence>`, which is stable
and collision-free under the existing actor sequence invariant.

`suggestion.review` has this payload:

```json
{
  "suggestion_id": "actor:suggestion:12",
  "decision": "accept",
  "operation_ids": ["actor:12", "actor:13"]
}
```

The latest causally ordered review for a suggestion wins. A rejection also sets
the review operation's `reverts` field to the reviewed operation IDs. The
materializer omits those IDs while retaining every original and review record.
An accept after a reject therefore restores the authored operations without
copying or deleting them.

Comments use the existing `comment.add`, `comment.reply`, and
`thread.set_status` operations. Their target is a versioned JSON anchor whose
type is `suggestion` and whose identity is the `suggestion_id`.

## Projection and rendering

The suggestion projector orders committed operations and groups only authored
notebook changes. Execution and comment operations do not create suggestions.
For each group it materializes the notebook immediately before the group and a
second snapshot with the group applied, then uses the notebook-aware diff model.

Selecting **Review suggestions** opens a separate virtual workspace tab with a
`suggestion://notebook/<encoded local URI>` identity. The editor tab remains
mounted, and reopening review focuses the existing suggestion tab through the
workspace controller's URI deduplication. Review tabs are intentionally not
restored after a page reload; the source notebook remains the durable document.

The review tab shows one suggestion at a time. A fixed-width left panel owns the
suggestion summary, previous and next navigation, accept and reject actions, and
the discussion thread. The notebook canvas independently scrolls on the right
and contains only the proposed notebook state. **Edit view** closes the review
tab and returns focus to its source notebook. Discussion cards follow the Google
Drive comments hierarchy: author and timestamp first, message content, indented
replies, then a compact reply composer.

Inserted cells use a green border; deleted cells use a red border and
strike-through. Text mutations use a whitespace-preserving word diff with green
insertions and red strike-through deletions. Linked-resource mutations are shown
as a deleted old cell followed by an inserted new cell because an inline text
diff would misrepresent the change.

## Concurrency

Suggestion IDs are authored locally and never inferred from wall-clock timing,
so concurrent editor batches do not collapse into one suggestion. Reviews are
ordinary causal operations. Concurrent decisions converge through the operation
log's deterministic order; the last ordered decision is the visible register.

Rejecting a create can leave later operations for that cell without a visible
base register. Those later operations remain in history and become effective if
the create is accepted again. This dependency-preserving behavior is preferable
to manufacturing compensating cell identities.

## Tradeoffs and follow-ups

The UI renders the proposed notebook for the active suggestion, retaining
unchanged cells as context while highlighting the cells owned by the suggestion.

Grouping is currently one debounced editor journal write. A future explicit
"suggesting" authoring mode can keep one suggestion open across several editor
writes by supplying the same `suggestion_id`.

The text differ caps dynamic programming at 400 tokens per side and falls back
to whole-value deletion/insertion for larger mutations. This bounds interactive
cost while preserving an accurate review.
